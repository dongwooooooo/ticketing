===== 비교 요약 =====
변형                     winner duration  GC total  contender p99
MaxGCPauseMillis=500     313 ms           115 ms    411 ms
MaxGCPauseMillis=50      257 ms            96 ms    330 ms

  - 두 변형 모두 winner 락 보유 시간이 250~310ms (heap pressure 포함). baseline
    (GC pause 없는 정상 reserve) ~5~20ms 대비 15~60배.
  - MaxGCPauseMillis=50 변형은 G1이 young GC를 더 잘게 쪼개 평균 pause는 줄었으나,
    동일한 heap pressure 워크로드에서는 총 GC 시간(96ms vs 115ms)과 대기 thread
    p99(330ms vs 411ms)에서 ~20% 개선에 그침. 락 보유 중 GC가 발생하면 어떤 튜닝
    으로도 대기 thread는 winner의 GC pause만큼 추가 대기를 한다.

===== 영향 분석 =====
영향: 락 보유 중 GC pause = 사실상 락 timeout 연장.
  - PostgreSQL FOR UPDATE 락은 application-level이 아니라 트랜잭션 단위라 STW로
    멈춘 JVM client의 락을 외부에서 깰 방법이 없다 (autovacuum/lock_timeout은
    설정 안 하면 무한정 대기).
  - Kleppmann DDIA §8 fencing token anti-pattern 의 단일 노드 변형: 락은 살아있지만
    holder가 STW로 멈춘 동안 다른 thread는 그 시간만큼 응답 지연.
  - 분산 환경이라면 더 심각: lease lock의 TTL이 GC pause보다 짧으면 lock holder가
    GC 끝난 뒤 자신이 lock을 잃었다는 것을 모르고 작업을 계속 (DDIA Fig 8-4).

===== 사용자 관점 결론 =====
사용자 A가 R열 1번을 클릭한 순간 서버 JVM에서 GC pause가 발생하면:
  - 평소 응답: 5~20ms 내 "예매 완료" 또는 "이미 선점됨" 메시지
  - GC pause 시: 같은 좌석 노리는 사용자 B는 ~330~411ms 동안 로딩 스피너 응시.
    동시 100명 환경에서 대기 thread p99가 정상치의 20~80배.
  - 단일 사용자에게는 "왜 이렇게 느리지?" 정도지만, 인기 좌석에 동시 100명이
    몰리면 락 직렬화 + GC pause가 누적되어 마지막 thread는 수 초 대기 후
    "이미 선점됨" 응답을 받음. (체감 UX: 사이트가 먹통)

===== anti-pattern §1.5 보강 결론 =====
비관적 락은 "lock holder의 wall-clock 시간"에 시스템 응답성이 종속된다.
holder JVM이 STW pause에 들어가면 락은 살아있는 채로 모든 대기자가 멈춘다.
완화책 세 가지:
  1. 락 보유 시간 최소화: 트랜잭션 안에서 heap 할당/외부 호출/I/O 금지.
     ReservationService.reserve() 처럼 SELECT FOR UPDATE → UPDATE → COMMIT 만.
  2. lock_timeout 설정: PostgreSQL `SET lock_timeout = '500ms'` 로 contender가
     무한 대기하지 않게 하고, 실패 시 즉시 사용자에게 "재시도" UX 반환.
  3. 분산 환경에서 fencing token 도입: lease lock 발급 시 monotonic token 부여,
     write 시 token 검증 (DDIA §8 Fig 8-5). 단일 노드라도 GC pause 후 stale
     holder가 commit하지 못하게 동일 패턴 적용 가능.

주의: contender 경로(ReservationService.reserve)는 CAS UPDATE 로 전환되었으나,
winner 경로는 동일 테스트가 직접 seatRepository.findByIdForUpdate(seatId) 를 호출하므로
비관적 락 보유 시나리오 자체는 유지. 즉 "락 보유자가 GC pause 에 들어갔을 때
CAS contender 가 얼마나 빠르게 풀려나는가" 를 새로 측정.

비관적 락 시점 vs CAS 차이:
- winner reserve duration: 313/257 → 226/226 ms. 양쪽 GC 변형 모두 28~12% 단축.
  heap pressure 작업 비중이 동일한데 락 보유자 자체가 winner thread (테스트가
  직접 FOR UPDATE 호출) 이므로 winner 측 절대 시간 변화는 G1 자체의 jitter 와
  JIT warm-up 효과. CAS 가 winner duration 을 직접 줄이지는 않음.
- contender p99: 411/330 → 235/236 ms. 약 43%/29% 단축.
  비관적 락 시점에는 contender 100개가 winner 의 FOR UPDATE 락 queue 에서 대기 →
  winner COMMIT 시점에 한꺼번에 풀리며 PG 가 순차 진행. CAS contender 는 winner
  의 UPDATE 윈도우(짧음)만 대기, 즉시 CAS miss 로 떨어져 application 단에서
  거절. 락 queue 직렬화가 사라지므로 GC pause 와 무관하게 contender 응답이 짧음.
- contender max: 411/330 → 235/236 ms 와 동일 수치. tail latency 가 cluster
  되어 winner queue 의 단계적 wake-up jitter 가 제거됨.
- GC pause 튜닝 효과: 비관적 락 시점은 pause=500 → 50 일 때 p99 411 → 330 (-20%)
  의 의미 있는 차이. CAS 시점은 235 → 236 으로 차이 없음.
  → GC 튜닝의 영향이 락 전략 변경으로 흡수됨. CAS contender 는 락 wait 가 아니라
    application-level fail-fast 경로라서 winner JVM GC 상태와 결합도가 낮음.

핵심 통찰: CAS 가 가장 크게 영향 준 시나리오. 비관적 락에서 "winner GC pause =
대기자 timeout 연장" 등식이 CAS contender 경로에서는 깨짐 (contender 는 lock queue
에서 안 기다리고 즉시 CAS miss 받음). DDIA §8 fencing token 의 단일 노드 변형
문제가 CAS 로 완화됨.
